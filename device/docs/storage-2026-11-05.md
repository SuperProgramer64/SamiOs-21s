# Historical CMD18 and persistent-data implementation

English consolidation of the initial storage notes. Physical speed and persistence were validated later; current status is in the top-level docs.

The DW-MMC driver added counted CMD23/CMD18 reads, bounded transfers up to 128 KiB, a 64 KiB comparison against CMD17 and automatic fallback after transfer cleanup. R1 status and timeouts are checked. CMD18 became the main read path; the later physical effective transfer rate was around 42 MiB/s.

`emmc_write=1 emmc_var_lba=N emmc_var_sectors=M` exposes a separate bounded data node rather than a writable whole-card device. Validation checks APFS size/margin, physical capacity, EXT_CSD user area, journaled HFS+ signatures and geometry. Requests crossing the window end are rejected entirely. Single-block writes wait for ready/transfer state and flush an enabled eMMC cache; uncertain writes are not blindly retried. Raw access uses kernel buffers and uiomove.

`var_hfs=emmc1` mounts persistent data through stage0; RAM remains a fallback if that mount fails. The initial installation had to rebuild init because an older prebuilt lacked this path. Kernel compilation alone would not have fixed that missing userspace behavior.

The tested system begins at absolute LBA 12216320 and occupies 2482311168 bytes. HFS+ data begins at 17068032, spans 3092480 sectors, and ends at the payload reservation at 20160512. Later a separate 4 MiB log reservation was established. These are descriptive measurements; always revalidate the actual logical-partition extents before writing.

`xnusys.py var-plan` computes geometry and arguments. Initial `var-write` requires an explicit device and acknowledgment, rechecks the layout, rejects existing primary or backup HFS signatures, and verifies readback. `var-verify` matches an initial unused image; after normal writes, the entire image should no longer match its initial hash. Root-image resizing is refused when it would collide with existing data.

The initial journaled HFS+ image was created and checked locally, not by mounting the phone data in write mode on macOS. It is never recreated during routine payload updates. The owner must keep private backups and original boot images.

MMIO-model tests exercise real read/write dispatch, error status, fallback, bounds, flush and interrupted-write cleanup under sanitizers. Device tests cover layout changes, existing-volume refusal and log selection. Some unrelated upstream provenance/device tests originally required private artifacts; those historical failures were not evidence that storage itself was verified on hardware.
